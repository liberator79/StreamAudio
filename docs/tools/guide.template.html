How StreamAudio works

A complete explanation of how this app shares audio from Windows or Android to another device over Wi‑Fi, what each technology is for, and a walkthrough of every line of the source code. The code below is the real code, with its real line numbers, so this page can be read without the project open.

1. What StreamAudio does

StreamAudio lets one device (the host) send whatever it's playing to one or more other devices (listeners) on the same Wi‑Fi network. Hosts can be a Windows PC or an Android 10+ phone; listeners can be Android phones or PCs. It is one Kotlin Multiplatform code base built with Compose Multiplatform for the UI.

2. The big picture

Audio flows left to right. Solid arrows are audio; dashed arrows are the small control messages the listener sends back.

  1. The host's AudioSource hands over raw audio in 5 ms pieces.
  2. HostEngine runs a dedicated high-priority thread that reads each piece and immediately gives it to UdpAudioServer.
  3. UdpAudioServer stamps a sequence number on it and sends one UDP datagram to every listener that has said HELLO in the last 4 seconds.
  4. On the listener, a network thread receives datagrams, drops late duplicates, counts losses and puts audio into the jitter queue.
  5. A separate playback thread takes audio from the queue at the speaker's own pace, writes it to the AudioPlayer, and throws away any backlog so the delay never creeps up.

4. The network protocol

Every datagram starts with a 4‑byte header. Anything that doesn't start with S A 1 is ignored.

BytesContent
0–1'S' 'A' magic
2protocol version (1)
3type: 1 AUDIO, 2 HELLO, 3 BYE, 4 DISCOVER, 5 HOST_INFO
4–7(AUDIO only) sequence number, big-endian

BYEboth waysListener: "stop sending". Host: "I'm stopping"; the listener shows Waiting for host and keeps sending HELLO so it resumes by itself when the host comes back.

AUDIOhost → listener5 ms of PCM with a sequence number, so the listener can detect lost and out-of-order packets.

5. Host pipeline

The host's only job is to move audio from the capture device to the network as fast as possible. There is deliberately no queue on the host: the capture thread reads 5 ms, sends it, and reads again. If anything is slow, audio is dropped rather than delayed.

  • Windows: SystemAudioSource tries WASAPI loopback first (captures the default speaker, no setup), then a JavaSound "Stereo Mix"-style device.
  • Android: AudioStreamService (a foreground service) obtains the MediaProjection and runs PlaybackCaptureSource.
  • Both feed the same shared HostEngine and UdpAudioServer.

6. Listener pipeline

The listener has two threads so that the network is never blocked by the speaker:

  • Network thread: blocks on receive() (200 ms timeout), validates and copies each packet into a recycled buffer, puts it on the queue, and sends HELLO once a second.
  • Playback thread: waits until the queue holds the target amount ("priming"), then repeatedly takes one packet and writes it to the speaker. The write blocks until the speaker has room, so this thread naturally runs at the speaker's real clock.

7. How lag is kept low

The previous version wrote packets straight to the speaker from the receive loop. Whenever the speaker was full, unread packets piled up in the operating system's socket buffer, which holds about a second of audio. Nothing ever removed them, so the delay grew whenever Wi‑Fi burst or the two devices' clocks drifted apart. The current design fixes that at every stage:

StageDelayTechnique
Capture5–10 ms5 ms reads; WASAPI loopback instead of DirectSound; no host-side queue.
Network1–5 ms on Wi‑FiUDP, one Wi‑Fi frame per packet, DSCP "EF" (voice) marking so routers with WMM prioritize it, Wi‑Fi lock on Android.
Jitter queue30 / 60 / 120 ms (+0–200 adaptive)Pre-buffer to the target; if the queue grows beyond target + slack, skip back to target (bounded latency). If it starves because of jitter, add 20 ms of headroom, and give 10 ms back after each 20 s without a dropout.
Output~20–40 msAndroid PERFORMANCE_MODE_LOW_LATENCY with a small buffer; 40 ms JavaSound line on desktop.
Measured in the automated tests on localhost: after a 400 ms host stall followed by a burst, the listener is back at ~45–75 ms. With delivery clumped every 100 ms (like a phone's Wi‑Fi in power-save), playback stayed uninterrupted at ~45–85 ms.

8. Finding hosts

The Listen screen broadcasts DISCOVER to 255.255.255.255 and to every network interface's subnet broadcast address (some routers only pass one or the other), three times over 1.5 s. Each host replies straight to the sender with HOST_INFO. If the router blocks broadcast (common on guest networks with "AP isolation"), you can still type the IP shown on the host screen.

9. Android specifics

  • Permissions: RECORD_AUDIO (required by Android for playback capture), the screen-capture consent dialog (MediaProjection), POST_NOTIFICATIONS (Android 13+, to show the service notifications), WAKE_LOCK and foreground-service permissions.
  • Hosting runs inside AudioStreamService, a mediaProjection foreground service. Android 14+ requires the service to be in the foreground before getMediaProjection() is called and allows each consent to be used once, which is why the consent is "consumed" there.
  • Listening runs inside ListenService, a mediaPlayback foreground service. Without it Android freezes the app when the screen turns off and the audio stops.
  • Power: while streaming, a partial wake lock keeps the CPU awake, a HIGH_PERF Wi‑Fi lock keeps the radio out of power-save with the screen off, and a LOW_LATENCY lock (Android 10+) further cuts latency while the screen is on.
  • Limits: apps can opt out of being captured (some streaming apps do), and capture needs Android 10+.

10. Windows specifics

  • WASAPI loopback is called through JNA (Java Native Access) by calling COM interface methods directly by their position in the vtable: IMMDeviceEnumerator → default render IMMDevice → IAudioClient (initialized with the LOOPBACK flag) → IAudioCaptureClient.
  • AUTOCONVERTPCM makes Windows convert from the device's mix format (often 32‑bit float, sometimes 44.1 kHz or 5.1) to our 48 kHz/16‑bit/stereo, so no conversion code is needed.
  • Loopback produces no data while nothing is playing; the listener simply plays silence and re-primes when sound resumes.
  • Windows Firewall must allow Java on private networks for listeners to reach the host.

12. UI & dark mode

All screens are shared Compose code. StreamAudioTheme chooses a hand-tuned Material 3 light or dark colour scheme from the System / Light / Dark switch (saved in settings). On Android, the status-bar icons and the launch window background follow the same choice, so there is no white flash in dark mode. The layout is limited to 560 dp wide, so it looks right on phones and in a wide desktop window.

13. Tests

composeApp/src/jvmTest runs the real networking code over localhost: server handshake and sequence numbers, discovery replies, end-to-end latency after a burst, adaptation to clumped delivery, WASAPI open/read, and repeated start/stop of real system-audio hosting. Run with gradlew :composeApp:jvmTest.

14. Code walkthrough

Files appear in the order the audio flows through them: protocol, then host, then listener, then platform glue, then UI. Expand "package declaration and imports" to see each file's first lines. Every other line is shown.

@@FILE composeApp/src/commonMain/kotlin/com/example/streamaudio/StreamProtocol.kt | StreamProtocol.kt: format & wire protocol@@ @@AT /**@@

StreamConfig is the single source of truth for the audio format. Both host and listener use these constants, so they can't disagree.

  • DEFAULT_PORT: the UDP port the host listens on.
  • SAMPLE_RATE, CHANNELS, BYTES_PER_FRAME: 48 kHz stereo 16‑bit, so one frame (one sample for each channel) is 4 bytes.
  • FRAMES_PER_PACKET = 240 gives PACKET_BYTES = 960 and PACKET_MS = 5. These are computed from each other, so changing one keeps the rest consistent.
@@AT /** Listener re-sends HELLO@@

Heartbeat timing: listeners say HELLO every second; the host drops any listener it hasn't heard from in 4 seconds (four missed heartbeats). That tolerates occasional packet loss while still cleaning up listeners that vanish without saying BYE.

@@AT /** How much audio@@

LatencyMode is the user-facing buffer choice on the Listen screen. targetMs is how much audio the listener tries to keep queued; label and description are shown in the UI.

@@AT /**@@

StreamProtocol builds and parses datagrams. The magic bytes and version let the app ignore unrelated UDP traffic on the same port. TYPE_* are the five message kinds from section 4. HEADER_SIZE is the 4‑byte common header; audio adds 4 bytes of sequence number, so MAX_DATAGRAM is 968 bytes. It is internal because only this module needs it.

@@AT fun writeHeader@@

Writes 'S' 'A' version type into the first four bytes of a buffer. Used for every outgoing message.

@@AT /** Returns the packet type@@

Validates an incoming datagram: too short, wrong magic or wrong version returns null (ignored), otherwise returns the type byte for a when to switch on.

@@AT fun control(@@

Builds a small control message (HELLO, BYE, DISCOVER, HOST_INFO) with an optional payload, such as the device name in HOST_INFO.

@@AT fun writeInt(@@

Stores a 32‑bit integer big-endian (most significant byte first), the conventional network byte order. Used for the sequence number.

@@AT fun readInt(@@

The inverse of writeInt. and 0xFF stops Kotlin's signed bytes from smearing their sign bits into the result.

@@AT /** Peak absolute amplitude@@

Computes the loudest sample in a chunk of PCM (0.0 = silence, 1.0 = full scale) for the level bars in the UI. Each 16‑bit sample is little-endian: the low byte is masked with 0xFF and the high byte is shifted left by 8 (keeping its sign). The loop steps 2 bytes at a time across both channels. It's very cheap, so it runs on every packet on both host and listener.

@@ENDFILE@@ @@FILE composeApp/src/commonMain/kotlin/com/example/streamaudio/UdpAudioServer.kt | UdpAudioServer.kt: host networking@@ @@AT /**@@

The host's UDP endpoint. onListenersChanged is a callback so HostEngine can show the listener count.

@@AT private val clients@@

The listener list: socket address → time of last HELLO. A ConcurrentHashMap because the control thread adds and removes entries while the capture thread iterates over them.

@@AT private val socket@@

Opens the socket in two steps: reuseAddress = true must be set before bind, so the port can be re-bound immediately after a stop (otherwise you'd get "address already in use"). The bind is done in also { } on purpose: inside apply { }, port would refer to DatagramSocket.getPort() (−1), a bug the tests caught. Then:

  • broadcast = true allows replying to broadcast discovery.
  • sendBufferSize = 64 KB is enough for bursts to many listeners.
  • trafficClass = 0xB8 marks packets DSCP EF ("voice"). Wi‑Fi access points with WMM put them in the highest-priority queue. It's wrapped in runCatching because some systems refuse it.
@@AT private val sendBuffer@@

One reusable buffer and DatagramPacket for all audio sends, so sending 200 packets per second creates no garbage. sequence counts packets.

@@AT private val hostInfo@@

The discovery reply, built once: "desktop|MY-PC" or "android|Pixel 8".

@@AT init {@@

Starts the control thread as a daemon thread, so it never keeps the app alive on its own.

@@AT private fun controlLoop@@

The control thread. soTimeout = 1000 wakes receive() every second even if nothing arrives, so stale listeners are pruned on schedule. packet.setLength(buffer.size) must be reset before every receive: Java shrinks a packet's length to the size of the last message, which would silently truncate later, larger ones. A closed socket throws IOException, which ends the loop.

@@AT private fun handleControl@@

Handles one control message:

  • HELLO: add the listener or refresh its timestamp. put returns null only for a new listener, which is when the count changes.
  • BYE: remove the listener immediately.
  • DISCOVER: reply with hostInfo to whoever asked.
@@AT private fun pruneStaleClients@@

Removes listeners whose last HELLO is older than 4 seconds, and publishes the new count if anyone was removed. now() is wall-clock milliseconds.

@@AT fun sendAudio@@

The hot path, called by the capture thread every 5 ms. The sequence number increments even with no listeners, so numbers stay continuous. With no listeners it returns early. Otherwise it writes the header and sequence, copies the PCM after it, and sends the same packet object to each listener by changing only its destination. A failed send is ignored: the heartbeat timeout handles truly dead listeners, and one failure must never stall the others.

@@AT fun stop()@@

Stops hosting cleanly. It snapshots the listeners, clears the list and reports 0. Then a short worker thread sends each listener a BYE and closes the socket, because Android forbids network I/O on the main thread, where stop() is usually called from. join(250) waits briefly so the port is free if the user starts hosting again straight away.

@@ENDFILE@@ @@FILE composeApp/src/commonMain/kotlin/com/example/streamaudio/HostEngine.kt | HostEngine.kt: host pipeline & state@@ @@AT enum class HostStatus@@

HostState is everything the Host screen shows: status, listener count, source name, live level, and a message for errors. It is an immutable data class, so each change is a new value and Compose recomposes reliably.

@@AT /**@@

The engine is deliberately simple: one thread, no queues, no coroutines in the audio path.

@@AT private class Session@@

A Session bundles one hosting run: its server, source, network lock and a @Volatile running flag that the capture thread checks. Using a fresh object per run means a slow-dying old thread can never affect a new run, since every update checks "am I still the current session?".

@@AT private val _state@@

The private mutable StateFlow plus a read-only view for the UI. session is @Volatile because it's read from several threads.

@@AT fun start(source@@

Starts hosting inside synchronized (so a double tap can't start twice):

  • Sets state to Starting.
  • Creates the server. A BindException means the port is taken (usually another copy of the app), so it shows a clear message.
  • Takes the network lock and creates the session.
  • Starts the capture thread. The source is opened on that thread, not here, so a slow device open never freezes the UI.
@@AT fun stop()@@

Takes the session out under the lock (so only one caller stops it), flags the thread to finish, stops the server (which sends BYE), releases the network lock and resets the state to Idle. The capture thread closes the audio source itself when it exits; closing it from here could pull it out from under a read() in progress.

@@AT /** Surfaces a problem@@

Lets Android's service report errors that happen before capture starts (no permission, Android refused the projection) so the Host screen can show them.

@@AT private fun captureLoop@@

The capture thread. It raises its priority to audio, then opens the source. On failure (for example "No system-audio capture device found") the run ends with an error state. On success it switches to Live and shows the real source name.

@@AT val buffer = ByteArray(StreamConfig.PACKET_BYTES)@@

The main loop, run while running:

  • read blocks for up to one packet. −1 means the device died (for example the speaker was unplugged), which becomes an error.
  • The read size is trimmed to whole frames, because sending half a frame would swap left and right channels from then on.
  • sendAudio sends immediately: the host keeps no queue at all.
  • The peak level is accumulated and published at most every 50 ms (20 times per second), which is smooth for the meter without flooding the UI.

Any exception while running becomes an error state. finally always closes the source on this same thread.

@@AT private fun fail@@

Error path: if this session is still current, it ends it (server, lock) and publishes an Error state with the message. If it isn't current (the user already pressed Stop), the error is ignored.

@@AT private inline fun updateIfCurrent@@

Updates state only while a session exists, and, when a session is given, only if it's the current one. This prevents a finishing old thread from overwriting a newer state.

  • AUTOCONVERTPCM | SRC_DEFAULT_QUALITY: Windows converts the mix format to ours.
  • A 100 ms buffer (in 100‑ns units). For capture this is just headroom; it adds no delay because the loop drains it continuously.

@@AT override fun read(@@

Fills the caller's buffer from pending. While there isn't enough data, it drains the device; if nothing new arrived it sleeps 2 ms. When enough data is ready, it copies one packet out and shifts the remainder to the front.

@@AT /** Moves every packet@@

Moves all audio WASAPI has ready into pending:

  • GetNextPacketSize (capture index 5): 0 means nothing is waiting.
  • GetBuffer (index 3) gives a pointer to the data, the frame count and flags.
  • If pending would overflow (the reader fell behind), the oldest audio is dropped: being current matters more than being complete.
  • The SILENT flag means "treat as zeros", so the data pointer may be garbage.
  • ReleaseBuffer (index 4) hands the space back to Windows.
@@AT override fun close()@@

@@AT /** Calls method@@

@@AT // ---------------------------------------------------------------- network@@

(Section divider.)

@@AT private fun networkLoop@@

The network thread starts by taking the low-latency network lock. It resolves the host and opens an unbound socket (the OS picks a free port). The 256 KB receive buffer is only a safety net, since this thread drains it continuously. A 200 ms timeout lets the loop do its timed work, and the voice DSCP marking is applied. If stop() raced ahead, it exits.

@@AT val hello = StreamProtocol.control@@

Prebuilt HELLO and BYE packets for this host, a receive buffer with some slack, and the loop's local state: last heartbeat time, last statistics time, expected next sequence number, and whether the host said BYE.

@@AT while (s.running) {@@

Each loop iteration first does the timed work:

  • HELLO once a second. This both subscribes and keeps the subscription alive. It keeps going while the host is away, so playback resumes automatically when the host returns.
  • Statistics to the UI 4 times a second.

Then it waits for a datagram. setLength is reset before every receive (see the server for why); the old code missed this, so one short packet would truncate every later one.

@@AT StreamProtocol.TYPE_AUDIO -> {@@

Handling an audio packet:

  • Rejects empty or oversized payloads.
  • Sequence check: a packet behind the expected number (late or duplicated) is dropped, because we've already played past that moment. A jump ahead counts the missing ones as lost. The ±1000 window treats huge jumps (host restarted, counter reset) as a fresh start.
  • Takes a chunk from the pool, copies the PCM in, and trims it to whole frames.
  • Queues it. If the 1 s hard cap is ever hit, the oldest chunk is dropped to make room: newest audio wins.

A BYE from the host marks it as gone. Any later audio clears that flag.

@@AT } catch (e: Exception) {@@

Errors become user-readable messages (unknown host, network error). finally always releases the network lock, sends BYE if possible, and closes the socket, all on this thread.

@@AT private fun publishStats@@

Works out what the UI shows:

  • Status: Connecting until the first packet; HostLost after BYE or 2.5 s of silence; otherwise Playing or Buffering, depending on the playback thread.
  • Loss %: over a rolling window that resets after 2000 packets, so it reflects recent conditions.
  • Delay: queued packets × 5 ms + the speaker's buffer.
  • Level: shown only while playing.
@@AT // ---------------------------------------------------------------- playback@@

(Section divider.)

@@AT private fun playbackLoop@@

The playback thread raises its priority to audio, opens the speaker, and records its buffer delay for the statistics.

@@AT // Adaptive headroom@@

The adaptive part: extra is headroom added on top of the chosen mode. underrunAt records when the queue last ran dry, and lastAdjust when headroom last changed.

@@AT while (s.running) {@@

Each iteration computes the target (mode + extra, in packets) and the slack (half the target, at least 20 ms) allowed before trimming.

Priming: after start or a dropout, nothing plays until the queue reaches the target, so playback starts with a full cushion. When priming completes shortly (under 1.5 s) after a dropout, the dropout was network jitter rather than the host going quiet, so 20 ms of headroom is added (up to 200 ms). While priming, the thread sleeps 2 ms between checks.

@@AT // Latency control:@@

The lag fix. If a Wi‑Fi burst or clock drift pushed the queue beyond target + slack, packets are discarded until the queue is back at the target. This bounds the delay; without it, a backlog would be heard as delay forever.

@@AT val chunk = s.queue.poll@@

Takes the next packet, waiting at most 30 ms. If none arrives, the queue starved: playback returns to priming and the time is recorded for the adaptive logic.

When the connection has been stable for 20 s, 10 ms of headroom is given back, so the delay returns to normal once conditions improve.

The chunk is written to the speaker. The write blocks until there's room, which paces this thread to the speaker's real clock. The level is measured, the chunk recycled, and the level published every 50 ms. finally always closes the speaker.

@@AT private fun fail@@

Ends the session with an error, if it's still the current one.

@@AT private companion object@@

Limits: the queue never holds more than 1 s (200 packets), and adaptive headroom never exceeds 200 ms.
